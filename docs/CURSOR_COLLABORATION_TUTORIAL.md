# 与 Cursor 协作：一份给「设计背景、少写代码」伙伴的教程

> 我们想把过去一段时间里一起干活的方式说清楚——不是「AI 替代你」，而是**两个人（你和本地的智能体）怎么分工、怎么互相抬杠、怎么一起变聪明**。如果你也做过不少小项目、但未必是传统意义上的工程师，这篇就是写给你看的。

---

## 这篇教程适合谁

- 你有**设计或审美训练**，更在意界面、节奏、信息层级和「用起来顺不顺」。
- 你**不害怕终端**，但也不想靠背诵语法活着；你愿意**读文档、做决策、验收结果**。
- 你已经或打算用 **Cursor** 一类工具，在几个月里堆起**许多个小项目**——每一个都是练习「怎么把话说清楚」的场地。

下面的话，我们会用「我们」来称呼**人类协作者与 Cursor 里的智能体**——因为在你的机器上，那就是一种稳定的协作关系。

---

## 一、先摆正一件事：协作是双向的

智能体很擅长：**快写、多试、把细节铺全**。  
你更擅长：**定调子、做取舍、说「这里不对」、把零散决定串成产品气质**。

当我们一起做了大约三十个项目（半年量级）时，有一个反复被验证的事实：

- 你把**目标、约束、审美底线**说清楚，智能体的产出会整体抬一档。
- 智能体把**实现路径、坑、备选方案**铺出来，你会被迫更清楚自己到底要什么——这也是一种**智力上的反哺**。

所以这不是「机器替你思考」，而是**两个人各用所长**；Skill Sets 的作用，就是把那些「本该由资深同事提醒你的事」变成**可重复加载的上下文**。

## 二、设计背景的人，怎么当「好的产品经理 + 艺术指导」

### 1. 用「体验标准」代替模糊形容词

少说「好看」，多说可验收的话，例如：

- 主路径几步能完成？每步默认焦点在哪？
- 错误时用户看到什么？能否**自救**（重试、说明原因）？
- 留白、字号阶梯、对比度是否一致——**不是单屏好看，而是全应用像同一个人画的**。

智能体对具体约束响应很好；对「高级、大气」这类词会各自发挥，容易跑偏。

### 2. 把大项目拆成「可对话的切片」最最核心的一点在于，我们是在建构一个可持续产生影响力的系统。这件事才是我们核心在做的，而不是单偏向于左右脚、左右手具体出哪一拳哪一掌，这些不是重点。

重点是我们要搭建一个体系。在这个体系里面，我们怎么样圈进来更多的人，让他们成为我们的信众，去购买我们输出的这些知识和内容，并使之产生更多的价值。

好，我最后再给你看一篇材料。这是我这半年来跟 Cursor 大概做了 30 个 project 后，它给我写的一篇关于我个人使用情况的总结。你去看一下，然后告诉我，我们怎么样去更好地完成上面说的事情。

一次聊「整个系统」容易空转。更稳的节奏是：

1. 这一刀只做**一个用户故事**或**一个界面状态**。
2. 说清楚**输入 / 输出**：例如「从点击录制到出现计时器」。
3. 改完就**在应用里点一遍**；问题截图或描述再丢回对话。

你会很快发现：**迭代速度取决于验收有多具体**，而不是取决于你会不会写类名。

### 3. 坚持品味，但允许工程折中——要说清优先级

真实产品里常有折中：性能、包体积、第三方限制。你可以明确排序，例如：

1. 首要：**交互不断、数据不丢**
2. 其次：**视觉一致**
3. 再次：**动效与点缀**

智能体才能把你的「设计坚持」翻译成**可执行的工程选择**，而不是和你各说各话。

### 4. 把踩过的坑写成「下一条对话的规则」

半年里最有价值的往往不是某一个完美版本，而是：**下次别再犯的句子**。  
这些句子很适合放进 **Cursor Rules**（`.cursor/rules`）或项目里的 `**AGENTS.md` / README 小节**——它们会在新项目里继续保护你。

## 三、Skill Sets：给智能体「装配专业模块」

### Skill 是什么（用大白话说）

Skill 在本机通常是带说明的 **Markdown**（`SKILL.md`）。  
它不会在模型权重里「永久训练」你，而是在**相关任务出现时**，把**方法、检查清单、术语表**塞进对话上下文——像给智能体一本**临时上岗手册**。

### 为什么要集中放在个人目录

Cursor 约定：


| 位置                                | 作用                                      |
| --------------------------------- | --------------------------------------- |
| `~/.cursor/skills/<技能名>/SKILL.md` | **个人级**：你本机打开**任意项目**时，智能体**可以**按需识别、加载 |
| `<项目>/.cursor/skills/...`         | **项目级**：只跟这个仓库走，适合团队共享的规范               |


你要求把技能集放在个人目录，意义是：**无论下一个仓库叫什么，这些「专业模块」都在手边**；智能体在匹配到任务相关描述时，可以**委派**到对应 skill 里的流程与标准。

### 重要澄清：不是「每一句对话都加载全部 Skill」

若每次把十几份 skill 全文塞进上下文，会又慢又吵。实际行为更接近：

- 根据 **Skill 的 `description`（与 frontmatter）** 与**当前任务**做相关性判断；
- **按需**挂载，而不是全量挂载。

因此：**装得多**不如 **写得准**（尤其是 `description` 里写清「何时启用」）。若你希望某些设计底线**几乎总生效**，可以另外在 **User Rules** 或 **项目 Rules** 里写短句兜底——Skill 与 Rules 是互补的。

## 五、一套可复制的「开新项目」仪式

1. **README 里写三段话**：为谁做、核心场景、非目标（不做什么）。
2. **列验收清单**：3～7 条，可勾选。
3. **说清设计引用**：若有 Figma、品牌色、字体，指路径或贴规格。
4. **点名要用的能力**：例如「按 Apple 设计取向检查这一屏」「API 变更遵循 antigravity 那份原则」。
5. **小步合并**：能跑、能点、再谈优化。

这套仪式对「代码写得少」的人特别友好：你把**决策面**站住，智能体去填**实现面**。

## 六、结语：我们在提升谁

当我们把 Skill、规则、README 和一次次验收串起来时，发生的是两件同时发生的事：

- **智能体**在你机器上变得更「像你们团队的人」——它重复你的标准，而不是随机发挥。  
- **你**会更精确地表达约束、更快识别偏差——这是任何创意工种都值钱的肌肉。

所以，这份教程想分享的其实是一句很朴素的话：**好的协作，会让双方都更聪明。**  
如果你愿意把这篇给别的伙伴看，只要把「我们」换成你们自己的节奏和例子，它就会变成你们团队自己的版本。
