# 脸部趣味 Effect：MediaPipe 精修 vs Jeeliz PoC 对比

本文档在**工程与产品约束**下，对比两条升级路径，供 DreamWorks（Electron + React、圆形 PiP、录屏、可拖拽）选型参考。  
**范围**：贴纸 / 面具类趣味 AR（非换脸级 Deepfake）。不涉及 Deep-Live-Cam、FaceFusion 等 Python 重管线方案。

---

## 一、背景与约束

| 约束 | 说明 |
|------|------|
| **体验目标** | 录制与 PiP **拖拽时保持顺畅**，主线程尽量少做重推理 |
| **现状** | 已使用 **MediaPipe** 做人脸关键点；Effect 为 **Canvas 2D 自绘**（如墨镜、萤火虫、爱心） |
| **痛点** | 部分 2D 效果满意度低；希望更有趣、仍可控资源 |

---

## 二、方案定义

| 方案 | 含义 |
|------|------|
| **A. MediaPipe 精修** | **保留**现有 MediaPipe（含 Worker / 降频策略），主要升级 **素材与绘制**：更精细的 2D、Lottie/SVG、或局部 WebGL 叠加，不引入第二套人脸引擎 |
| **B. Jeeliz PoC** | 引入 **[Jeeliz Face Filter](https://github.com/jeeliz/jeelizFaceFilter)** 类 **WebGL 实时面具管线**，与现有画布关系需二选一或合成：**替换渲染**或 **双路并行**（需评估 GPU） |

---

## 三、与现有架构的衔接

| 维度 | 方案 A（MediaPipe 精修） | 方案 B（Jeeliz PoC） |
|------|--------------------------|----------------------|
| **人脸跟踪** | 继续 MediaPipe，无需新模型栈 | 可能 **重复**：Jeeliz 自带跟踪，或与 MediaPipe **分工**（仅一处做脸姿） |
| **主线程** | 推理已在 Worker 则主线程主要是 **合成与绘制** | WebGL 通常在主线程或专用 canvas；需明确 **是否停用一路跟踪** 避免双倍成本 |
| **PiP / 圆形裁切** | 与当前 **同一套** 输出纹理/canvas 流程，改动面小 | 需把 Jeeliz 输出 **对齐** 到现有 PiP 尺寸、镜像、圆角遮罩 |
| **拖拽降频** | 已有思路可沿用：**拖拽时拉长推理间隔 / 降分辨率** | 同样需要对 Jeeliz 侧 **fps / 分辨率** 做对称策略，否则 GPU 仍可能尖峰 |

---

## 四、资源与流畅度（录制 + 拖拽）

| 指标 | 方案 A | 方案 B |
|------|--------|--------|
| **CPU** | 增量小（不新增人脸引擎） | 取决于是否 **双跑** 跟踪；若只用 Jeeliz 跟踪并下掉 MediaPipe 绘制链，可能 **互有增减** |
| **GPU** | 2D Canvas 为主时较低；若加局部 WebGL，中等 | **WebGL 持续占用**，多路合成时需注意 **Electron + Chromium** 的 GPU 预算 |
| **内存** | 主要随 **素材体积** 增长 | 随 **Jeeliz 资源与 runtime** 增长，需实测 |
| **集成风险** | 低 | **中与高**：双管线、时序同步、权限与摄像头 **单开/双读** 问题 |

**结论（资源向）**：在「不牺牲拖拽顺滑」前提下，**方案 A 默认更稳**；方案 B 可行但 **必须以 PoC 压测**（拖拽中 fps、掉帧、风扇）再决定是否合入主分支。

---

## 五、趣味性与效果上限

| 维度 | 方案 A | 方案 B |
|------|--------|--------|
| **2D 贴纸** | 上限取决于 **设计与动画**，可做精致墨镜、胡子、动态贴纸 | 非 Jeeliz 强项时可仍用 MediaPipe + Canvas |
| **3D 面具 / 立体跟脸** | 需自研或引入 **单点 WebGL**，工作量分散 | Jeeliz 生态偏 **3D 面具**，**趣味感**往往强于简单几何形 |
| **换脸级真实融合** | **不是**这两条路径的目标 | **不是** Jeeliz 主场景；换脸应另独立项 |

---

## 六、工程成本与周期（量级估计）

> 以下为 **粗量级**，便于排期；实际以代码现状与设计师产出为准。

| 项目 | 方案 A | 方案 B |
|------|--------|--------|
| **前期调研 + PoC** | 0.5–1 周（定 KPI、改 1–2 个标杆效果） | **2–4 周**（接摄像头、对齐 PiP、测拖拽与录制） |
| **合入产品 + 设置项** | 小 | 中（后端切换、降级路径、错误提示） |
| **维护** | 低（栈不变） | 中（依赖升级、GPU 差异、Issue 跟进） |

---

## 七、风险清单

| 风险 | 方案 A | 方案 B |
|------|--------|--------|
| 效果仍「不够好玩」 | 中（依赖美术与动效） | 低（3D 面具潜力大） |
| 拖拽/录制卡顿 | 低 | **高**（若不控 fps / 分辨率 / 双跟踪） |
| 与现有代码冲突 | 低 | **中–高**（渲染路径、时钟、镜像） |
| 许可与合规 | 低（注意 MediaPipe 与素材版权） | **需读 Jeeliz 许可证**并保留声明 |

---

## 八、建议的客观 KPI（PoC / 回归必测）

在 **同一台目标机**（如主力 Mac）上记录：

1. **PiP 拖拽中**：主线程 **长时间任务（>50ms）** 次数 / 秒，或 Performance 面板体感掉帧。  
2. **录制中**：目标 **输出帧率** 是否稳定（或与 CPU 占用曲线对照）。  
3. **固定分辨率档**：例如 480p / 720p 输入下，**推理间隔** 与 **端到端延迟** 上限。

方案 B 通过标准建议：**不低于**当前方案 A 在同 KPI 下的表现，或明确仅在「插电 / 高性能模式」开启。

---

## 九、三条执行建议（与之前评估一致）

1. **先方案 A 做 1–2 个标杆 Effect**（精修跟脸精度 + 动效），成本低且直接验证「到底是库不行还是资产不行」。  
2. **若仍不满意再开方案 B PoC**，且 PoC 阶段就定死：**单跟踪源**（MediaPipe **或** Jeeliz，避免双份人脸计算）。  
3. **任何新方案都绑定 KPI**，避免凭主观「好玩」合入导致录制路径回归。

---

## 十、推荐结论（文档层拍板）

| 优先级 | 建议 |
|--------|------|
| **默认路径** | **方案 A（MediaPipe 精修）**：与现有 Worker/降频策略一致，风险最低。 |
| **可选增强** | **方案 B（Jeeliz PoC）**：在 A 仍不达「趣味」目标时启动；以 GPU 与单跟踪源为硬约束做技术验证。 |
| **不推荐** | 在 PiP 录制主路径上叠 **第二套完整人脸 TF.js 栈** 或与 **Python 换脸** 硬绑，除非单独产品形态。 |
